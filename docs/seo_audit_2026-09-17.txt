ROOT CAUSE ANALYSIS
================================================================================
The site is a Vite/React single-page app (SPA) hosted on Vercel, with a
catch-all rewrite (`vercel.json`: "source": "/(.*)" -> "/index.html") that has
no exclusions. This one configuration choice explains most of the technical
findings below, independently discovered by multiple specialist passes:

  - /robots.txt, /sitemap.xml, and ANY nonexistent URL all return HTTP 200
    with the homepage's HTML shell instead of a real file or a 404.
  - There is no per-route head management (no react-helmet or equivalent),
    so all 17 routes share ONE <title>, ONE meta description, and ONE
    canonical tag — and that canonical points at a URL that itself
    308-redirects elsewhere (apex vs www mismatch).
  - Google's own index still shows a STALE snippet for the brand query:
    "Sunrise School | Under Construction" — the site currently does not
    rank for its own brand name at all.
  - Raw HTML ships ~7 words; all real content requires JS execution, which
    AI answer engines (ChatGPT Search, Perplexity, Claude search) mostly do
    NOT perform — so the school is effectively invisible to them today.

A second, independent problem sits on top of the technical one: CONTENT
INTEGRITY. The /alumni page lists named "graduates" (a surgeon at AIIMS, a
Google engineer, an "Alumni Tech Summit" at the Grand Hyatt Mumbai) with
fabricated companies, for a school that only offers a Commerce stream from
Std 11 onward. This reads as unedited placeholder/demo content shipped to
production. Under Google's E-E-A-T guidance this is a "Lowest quality /
deceptive purpose" signal that drags down trust for the ENTIRE site, not
just that one page — verify or remove immediately.

Confirmed directly against the source repo (D:\projects\sunriseschool):
  - frontend/vercel.json contains exactly the catch-all rewrite described
    above, with no exclusions for /robots.txt, /sitemap.xml, or 404s.
  - frontend/public/ contains only favicon.svg, icons.svg, and images/ —
    no robots.txt or sitemap.xml file exists in the build output.
  - frontend/src/App.jsx enumerates 23 static routes (no dynamic params),
    used to build the sitemap below.
  - Two orphaned page components exist in frontend/src/pages/ but are not
    wired into any route: AboutPage.jsx, ContactPage.jsx.
  - The broken brochure link points at frontend/Lab_1.pdf (note: actual
    filename is "Lab_1.pdf", capital L — the site links to "/lab_1.pdf"
    lowercase, which will 404/serve-shell on a case-sensitive host even
    once a real robots/sitemap fix is deployed. Verify the exact deployed
    path and filename case match.)

1. TECHNICAL SEO  (Score: 28/100)
--------------------------------------------------------------------------------
CRITICAL
  - No real robots.txt or sitemap.xml exists. All candidate paths
    (/robots.txt, /sitemap.xml, /sitemap_index.xml, /wp-sitemap.xml) return
    HTTP 200 with the SPA's index.html shell, not a real text/XML file.
  - Universal soft-404: a deliberately fake URL
    (/this-page-does-not-exist-xyz123) returns HTTP 200 with the identical
    homepage shell (same ETag/Last-Modified) instead of a 404. /admissions
    specifically renders visible "404 - Page Not Found" text while still
    returning HTTP 200.
  - Identical <title>, meta description, and <link rel="canonical"> on
    EVERY route (verified on /, /about, /contact, /inquiry, /academics/*,
    /results/*, /transportation, etc.) — no per-route head management.
  - Canonical tag points to the non-www apex (https://sunriseschoolrajkot.com/),
    which itself issues an HTTP 308 redirect to the www subdomain — a
    self-contradicting signal. Google actually indexed the www version.
  - Zero structured data (0 JSON-LD blocks) on raw AND fully-JS-rendered HTML.

HIGH
  - No SSR/prerendering — all ~17 routes are 100% client-rendered with no
    fallback content; content depends entirely on Google's deferred
    rendering queue (not immediate; hours-to-days lag).
  - 2-hop redirect chain on the plain-HTTP entry point
    (http -> https apex -> https www). Should be a single hop.
  - LCP-critical hero image (495 KB) is set via inline CSS
    background-image by React at runtime — invisible to the browser until
    the JS bundle downloads/executes/hydrates. No preload/preconnect hints
    anywhere in the HTML.

MEDIUM
  - Missing security headers: no Content-Security-Policy, no
    X-Content-Type-Options, no X-Frame-Options, no Referrer-Policy, no
    Permissions-Policy (Vercel zero-config defaults).
  - Monolithic 613 KB JS bundle (170 KB Brotli-compressed), no code-splitting
    — 57% of it (97.6 KB) is unused on the homepage alone.

LOW
  - No IndexNow key/integration for Bing/Yandex/Naver.
  - HSTS present (max-age=63072000) but missing includeSubDomains/preload.
  - Broad Access-Control-Allow-Origin: * set on the HTML document itself
    (not just static assets) — minimal SEO impact, worth a review.

5. PERFORMANCE / CORE WEB VITALS
--------------------------------------------------------------------------------
Lighthouse scores: 62/100 mobile, 92/100 desktop (lab data; no CrUX field
data available — no Google API key configured, and the domain is likely
below CrUX's minimum sample size anyway).

  Metric      Mobile (throttled)   Desktop   "Good" threshold   Status
  LCP         6.4s                 1.6s      <=2.5s              FAIL (mobile)
  CLS         0                    0.008     <=0.1               PASS
  INP (proxy) TBT 400ms             TBT 40ms  <=200ms             At risk (mobile)

The huge mobile/desktop gap proves this is a NETWORK-PAYLOAD problem, not a
code-architecture problem.

CRITICAL
  - Hero LCP element is a React-set inline CSS background-image, not a real
    <img> in initial HTML. 70% of the 6.4s LCP is "browser doesn't know
    about this image until the SPA hydrates and paints it." Zero preload
    hints, zero fetchpriority="high" anywhere on the page.
  - Images are 9.35 MB of a 9.5 MB total page (98% of page weight),
    massively oversized for their display size:
      * Logo displayed at 68x68px, served at 1.33 MB full-resolution JPEG
      * IMG_4768.JPG displayed at 362x443px, served at 3.13 MB
      * IMG_0402.JPG displayed at 362x443px, served at 2.78 MB
      * olympiads.png displayed at 362x114px, served at 810 KB
      * favicon.png: 197 KB (favicons should be <10KB)
    Root cause: raw camera/WhatsApp photos (filenames like IMG_4768,
    IMG-20250823-WA0010 — visible in frontend/src/assets or frontend/images)
    dropped straight into the Vite build unresized, bypassing the
    Cloudinary pipeline already set up for one image. FIX: resize to actual
    display size (x2 for retina), convert to WebP/AVIF, route through
    Cloudinary (f_auto,q_auto,w_<n>) — removes ~8MB and is the single
    biggest lever available.

HIGH
  - No route-based code splitting — one monolithic 613KB/170KB(gzip) JS
    bundle; 57% (97.6KB) unused on the homepage alone. Drives TBT to
    400ms under mobile CPU throttling (longest single task: 468ms). Fix in
    Vite: convert route imports in App.jsx to React.lazy()/dynamic import.

MEDIUM
  - Render-blocking stylesheet (14KB transferred / 104KB raw) — ~309ms
    estimated savings if inlined/async-loaded.
  - Unnecessary third-party request: transparenttextures.com background
    texture (146KB, cross-origin) for a purely decorative pattern. Replace
    with an inline SVG/CSS pattern or a <5KB locally-hosted tile.
  - Cache lifetimes on the few resources with explicit headers (Cloudinary
    image, texture PNG) are only 30 days — extend once on a CDN.

LOW / STRENGTHS
  - DOM size healthy (520 elements). CLS essentially zero — genuine
    strength, keep explicit width/height on new images.
  - Text compression already effective (72-87% ratio via Brotli).
  - Server/CDN TTFB is fast (50ms) — backend is NOT a bottleneck.

TOOLING NOTE: unlighthouse_run.py fails on Windows in this environment
